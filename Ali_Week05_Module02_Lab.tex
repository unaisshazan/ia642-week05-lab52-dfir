\section*{Lab overview}

This lab builds \texttt{MERIDIAN-APP01} (Windows Server 2022) on \texttt{meridian-lab-net}, stages a LOLBin-typical \texttt{certutil} execution trail and an HKCU Run-key persistence entry, acquires live memory with WinPmem, triages the image with Volatility~3, parses Prefetch and Amcache, and performs a static survey of the inert \texttt{svcupdate.bin} stand-in. Evidence \#1--\#7, three critical-thinking answers, a taxonomy classification, and a graded hunt hypothesis follow.

MERIDIAN-APP01 was installed from the Windows Server 2022 Evaluation ISO (Desktop Experience), attached only to \texttt{meridian-lab-net} for lab traffic, with a NAT adapter used solely to stage tools from the host. Directories \path{C:\Meridian} and \path{C:\Meridian\evidence} were created. Staging wall-clock time was recorded before artifact generation.

\labstep{Critical thinking \#1}

In the acquisition-time \texttt{pstree}/\texttt{cmdline} output, \texttt{certutil.exe} had already exited (expected for short \texttt{hashfile} runs), while \texttt{winpmem.exe} appears under the interactive Administrator session used for live acquisition (PID 2164; console-launched imager parentage, not a service or Office parent). \texttt{windows.malfind} returned multiple \texttt{PAGE\_EXECUTE\_READWRITE} regions: several under \texttt{MsMpEng.exe} (Microsoft Defender, PID 2488), plus additional RWX hits in \texttt{ServerManager.exe}, \texttt{wmiprvhost.exe}, and \texttt{wsmprovhost.exe}. Per the module lecture, Defender RWX regions are a known false-positive class and do \emph{not} by themselves demonstrate attacker process injection. The non-Defender RWX hits are also consistent with legitimate Windows management/remoting components on a freshly built server and likewise do not prove staged LOLBin or Run-key activity injected code. Local \texttt{certutil} execution and the HKCU Run key leave no injected-VAD signature once those processes exit, so a malfind view dominated by Defender and built-in management hosts is the expected outcome for this staging and must not be over-read as ``no attacker activity'' or as confirmed injection.

\labstep{Taxonomy classification}

\textbf{Classification: loader / downloader.}

Three static indicators:
\begin{enumerate}
  \item Banner string \texttt{MeridianLoader/2.1 (c) internal build} names the component as a loader family rather than ransomware or a worm.
  \item UTF-16LE marker \texttt{MRD-STAGE2-INIT} is a stage-2 handoff token typical of multi-stage loaders that initialize a subsequent payload.
  \item Embedded C2-style hostname \texttt{sync-update.meridian-relay.test} is a retrieval/beacon endpoint indicator aligned with downloader behavior, not encryption or kernel rootkit structures.
\end{enumerate}

The file is only a minimal \texttt{MZ} stub (not a valid PE), matching the lab's inert stand-in: structural taxonomy signals without runnable code.

\labstep{Critical thinking \#3}

\begin{enumerate}
  \item Weakest sole classification evidence: the leading \texttt{MZ} bytes. Benign Windows binaries also start with \texttt{MZ}, so that marker alone does not support malware taxonomy.
  \item Strongest loader/downloader-specific indicator: the combination of the \texttt{MeridianLoader/2.1} banner with \texttt{MRD-STAGE2-INIT}, which encodes staged loading rather than ransomware notes, worm replication, or backdoor implant language by itself. The C2 hostname further supports remote retrieval over other categories.
\end{enumerate}

\labpart{5. Graded challenge: hunt hypothesis}

\textbf{Claim.} After Parts A--C, MERIDIAN-APP01 shows operator-visible HKCU Run-key
persistence (\texttt{MeridianSyncHelper}) and LOLBin execution evidence, but memory
triage did not show injected code. A second, quieter persistence mechanism that
would survive interactive logoff and avoid the Run key is a user or system
Scheduled Task whose action launches \texttt{powershell.exe} or a lookalike helper
under a benign task name.

\textbf{Next artifact.} Enumerate scheduled task XML under
\path{C:\Windows\System32\Tasks} and the Task Scheduler registry keys
(\path{HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache}),
searching for task actions that reference \texttt{powershell.exe},
\path{C:\Meridian}, or \texttt{sync-update.meridian-relay.test}. This fits the
evidence because the staged Run key already abuses PowerShell for silent upkeep,
and task XML is a parallel ATT\&CK persistence class that would not appear in the
HKCU Run query we already ran, nor necessarily in a clean \texttt{malfind}.

\textbf{Negative result.} If no such task exists, the investigation still advances:
the Run key remains the only confirmed persistence on this host from Parts A--B,
narrowing follow-up to service \texttt{ImagePath} values and WMI subscriptions
rather than re-checking Run keys. Either outcome converts a vague ``quieter
persistence'' concern into a tested, closed question grounded in disk artifacts
memory alone cannot settle after process exit.
